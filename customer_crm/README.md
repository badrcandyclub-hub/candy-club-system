# قاعدة عملاء كاندي كلوب

## الفكرة وطريقة الاستخدام

ملف واحد لكل رقم موبايل، حتى لو العميل اشترى منتجات وهدايا، أو جاء من أكثر من مصدر. الاسم وحده لا يدمج العملاء. يدعم الأرقام العربية وصيغ 01 / +20 / 0020، ولا يخلط السجلات بلا أرقام صحيحة.

التقسيم على محاور مستقلة:

| المحور | أمثلة | فائدته |
| --- | --- | --- |
| العلاقة | عميل حالي / عميل محتمل | عملاء شوب وطلبات الذين اشتروا بالفعل يسجلون كعملاء حاليين |
| نوع المشتريات | منتجات / هدايا / الاثنان | مستخرج من سجلات النظام؛ العميل قد يظهر في القسمين |
| المصدر | إنستاشوب، طلبات، الفرع، واتساب، مصدر تكتبه | اختيار الجمهور حسب مكان معرفة العميل |
| الاهتمام | كاندي، شوكولاتة، بوكيهات، ليجو… | وسوم مرنة يذكرها العميل أو يسجلها الفريق؛ لا تُستنتج تفضيلاته تلقائيًا |
| المتابعة | جديد، تم التواصل، مهتم، متابعة لاحقة، متوقف | تنظيم العمل اليومي مع موعد للمتابعة |
| استقبال العروض | غير محدد / يسمح / لا يرغب | تجهيز جمهور محدد للعروض |

## ما تم تنفيذه

- واجهة مستقلة في بوابتي المدير والموظف، تُحمّل عند فتح قسم العملاء، وتعرض ١٢ عميلًا في الصفحة. على الموبايل تتحول الصفوف لتنسيق مختصر.
- بحث عربي بالاسم أو الرقم أو المنطقة أو الوسوم، وفلاتر للمصدر والاهتمام والمتابعة. ترتيب بالأحدث، عدد الطلبات، قيمة الطلبات، عدد الهدايا أو قيمتها.
- ملف العميل يعرض بيانات الاتصال، مصادره، ملاحظاته وموعد متابعته، وسجل الطلبات والهدايا في تبويبين. تُحمّل أسماء منتجات طلباته عند فتح ملفه فقط.
- إجمالي قيمة الطلبات يستبعد «ملغي» و«مرتجع» وفق قاعدة العد الموجودة، ويشمل الشحن حسب final_total. لا يُسمى مدفوعات أو مبالغ محصلة. VIP يعني ٣ طلبات غير ملغاة/مرتجعة أو أكثر.
- قيمة الهدايا منفصلة، من قيمة سجلات البيع المسجلة في gifts، مثل تقرير الهدايا الحالي. لا تُجمع بقيمة الطلبات لعدم وجود رابط مضمون يمنع حساب نفس البيع مرتين.
- سجلات دليل الهدايا المحلي تفيد في بيانات الاتصال والملاحظات، مع توضيح مصدرها المحلي. مبالغ هذا الدليل لا تُجمع مع مبيعات الهدايا السحابية.
- العميل الحالي بلا سجل مشتريات مفصل يظهر برسالة «تفاصيل الشراء غير مسجلة». لا تُختلق له مشتريات تاريخية.
- إضافة سريعة بالاسم والرقم؛ بيانات العنوان والمتابعة والملاحظات اختيارية. رقم العميل في التعديل ثابت لحماية ربط سجله.
- تصنيف العملاء المحددين بإضافة مصادر أو اهتمامات أو تعديل حالة المتابعة، مع الاحتفاظ بالوسوم الحالية. حتى ٢٠٠ عميل في العملية.
- قالب CSV فارغ، ومعاينة الاستيراد قبل الحفظ، وكشف الرقم المكرر داخل الملف أو الموجود في النظام. الاستيراد يضيف فقط ولا يستبدل العملاء الموجودين.
- تصدير البيانات المحددة أو نتائج الفلاتر. جمهور العروض يتضمن الأرقام الصالحة المسجل لها السماح بالعروض فقط، ويمكن تجهيزه في خانة الأرقام المخصصة بالحملات. تجهيز المسودة لا يبدأ الإرسال.

## إدخال البيانات دون تضييع وقت

ابدأ بتحميل [القالب الفارغ](customers-template.csv) أو زر «قالب فارغ» من الشاشة. الاسم والموبايل مطلوبان، وبقية الحقول اختيارية. النوع الافتراضي «عميل حالي»، لذا لا تحتاج ملء هذا العمود لعملاء شوب وطلبات السابقين.

في Excel اجعل عمود الموبايل «نص» قبل كتابة الأرقام، واحفظ CSV UTF-8. التاريخ بصيغة YYYY-MM-DD. الوسوم والمصادر المتعددة تفصل بينها فاصلة عربية «،». الحد ٢٠٠ صف و٢ ميجابايت للملف. راجع تقرير الصفوف المستبعدة ثم اضغط «حفظ الصفوف الصحيحة».

القيم المقبولة في الأعمدة الاختيارية:

| العمود | القيم العربية |
| --- | --- |
| نوع العميل | عميل حالي، عميل محتمل |
| حالة المتابعة | جديد، تم التواصل، مهتم، متابعة لاحقة، متوقف |
| التواصل التسويقي | غير محدد، يسمح بالعروض، لا يرغب في العروض |

لو لديك عدد كبير من العملاء بالفعل، فلتر المصدر، وحدد الصفحات المطلوبة، واضغط «تصنيف المحدد» لإضافة نفس الاهتمام دفعة واحدة. لا تدخل إجماليات شراء تخمينية في الملاحظات على أنها حسابات فعلية.

## تفعيل الحفظ المشترك في Supabase

**لم يتم تشغيل الترحيل على قاعدة الإنتاج من هذه المهمة.** لا توجد جلسة Supabase إدارية متاحة لتنفيذ SQL هنا.

1. شغّل محتوى [ملف الترحيل](../supabase/migrations/20261027_customer_crm.sql) في SQL Editor لمشروع Supabase الحالي.
2. انشر ملفات HTML وapp.js وcustomer_crm/ معًا. روابط الأصول في البوابتين تحدّثت.
3. سجّل الدخول من جديد بحساب نشط له صلاحية customers أو ALL، ثم افتح قاعدة العملاء واضغط تحديث.
4. جرّب إضافة عميل اختبار وتعديل ملاحظته من جهاز آخر، ثم استيراد ملف صغير ومراجعة المكرر قبل استيراد الدفعات الكبيرة.

الترحيل ينشئ customer_crm_profiles ودوال قراءة وحفظ فقط. لا يعدل جداول customers أو orders أو gifts، ولا معادلات الحساب أو التسوية. يتم الحفظ المشترك عبر RPC يتأكد من اسم المستخدم وكلمة المرور وصلاحية العملاء وفق نظام تسجيل الدخول الموجود. RLS مفعّل، ولا توجد صلاحية قراءة/كتابة مباشرة عامة على الجدول الجديد. لا تُخزن كلمة المرور في سجل العميل.

expected_revision يحمي من استبدال تعديل أحدث. دفعة الحفظ ذرّية: إذا تعارض صف، لا يُحفظ باقيها جزئيًا. فتح الصفحة بدون تفعيل الترحيل يتيح عرض المشتريات مع رسالة واضحة، ويوقف أزرار الحفظ والاستيراد.

## التحقق وحدوده

تم اختبار دمج الأرقام، العد والمبالغ المنفصلة، استبعاد الملغي والمرتجع، سجل الهدايا المحلي، CSV بعلامات التنصيص والأسطر المتعددة، الأخطاء والمكرر، منع حقن صيغ الجداول، والبحث العربي. اختبارات DOM ببيانات وهمية غطت الترقيم وملف العميل والحفظ والتصنيف الجماعي والاستيراد والتصدير وحالات تعطل الاتصال.

تم تنفيذ SQL مرتين في PostgreSQL تجريبي داخل الذاكرة والتحقق من الصلاحيات، الأرقام، رفض التعارض، ذرّية الدفعة، وحدود المدخلات. لم تُكتب بيانات عملاء إنتاجية ولم تُرسل رسائل. المراجعة البصرية الفعلية على المتصفح والموبايل لم تكتمل بسبب تعذر الاتصال بمعاينة المتصفح المدمج، وانتهاء مهلة موافقة الوصول إلى Chrome.

## التطوير التالي المقترح

بعد التفعيل واستخدام بيانات حقيقية، يمكن إضافة سجل مشتريات شوب وطلبات القديم من ملف طلبات منفصل مع رقم طلب ومصدر لمنع التكرار. كذلك يمكن إضافة شرائح مشتريات تلقائية من أصناف الكتالوج، وحفظ فلاتر الفريق المعتادة، وسجل تغييرات مفصل للمتابعة. هذه امتدادات لاحقة؛ ليست بيانات أو خصائص مفعّلة في الإصدار الحالي.
